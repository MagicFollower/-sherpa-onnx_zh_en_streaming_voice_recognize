# 03 技术选型与模型评估

## 1. 选型问题与评价原则

本项目不是寻找脱离硬件与语料的“全球最准模型”，而是在普通CPU、普通话混说、手机LAN和低等待约束下寻找可交付候选。
用户确认普通无独显电脑优先、实时优先、第二遍默认关闭；模型和框架组合为建议基线，实际质量与性能待实测。
研究访问日2026-09-21；所有网页版本及证据性质见00_阶段一导读与决策登记.md第7节“集中来源台账”。
本篇覆盖R01、R02、R14、R18、R19；放行对应A01、A02、A14、A18、A19。
评估顺序是许可与可运行性、领域质量、实时性、资源和稳定性，不能只凭参数量、新旧、星数或宣传排名。

### 1.1 必须区分的实时机制

| 机制 | 处理方式 | 主要成本与边界 |
| --- | --- | --- |
| 原生流式 | 分块输入，维护编码器或解码器流状态 | 有look-ahead和模型chunk等待，仍须测首字 |
| 滚动窗口实时封装 | 对重叠或累计音频反复识别，用确认策略稳定输出 | 重编码、回看和文本对齐成本随策略变化 |
| 两遍识别 | 流式草稿加离线声学精修 | 更高内存、尾部等待和状态管理成本 |
| 标点后处理 | 在ASR文字上恢复标点 | 不等于第二遍ASR，仍占计算和等待预算 |
| ITN | 将口语形式变为数字、日期等书面形式 | 可能改错关键字段，需要独立规则与测试 |

模型训练支持流式不等于公开推理wrapper具有恒定增量成本。
0.48秒刷新、8秒预览窗口、20ms网络帧和首个非空partial是不同量，不能互换。
原生流式也可能因CPU线程争用、VAD配置或beam过大而迟滞；窗口方案也可以有真实实时产品，但不能混称同一种机制。

## 2. A主选：sherpa-onnx双语Streaming Zipformer

### 2.1 推荐组合

模型标识：sherpa-onnx-streaming-zipformer-bilingual-zh-en-2023-02-20。
选择理由是原生流式、具体Windows CPU路径和可控组件组合，不是已经证明其手机混说准确率最高。
S01、S02、S03支持运行时、模型和制品信息；模型日期为2023-02-20，网页与revision尚未冻结。
https://github.com/k2-fsa/sherpa-onnx
https://k2-fsa.github.io/sherpa/onnx/pretrained_models/online-transducer/zipformer-transducer-models.html
https://huggingface.co/csukuangfj/sherpa-onnx-streaming-zipformer-bilingual-zh-en-2023-02-20

| 组件 | 官方INT8示例采用的文件 | 注意事项 |
| --- | --- | --- |
| 编码器 | encoder-epoch-99-avg-1.int8.onnx | INT8 |
| 解码器 | decoder-epoch-99-avg-1.onnx | 浮点，不写成全INT8 |
| Joiner | joiner-epoch-99-avg-1.int8.onnx | INT8 |
| Token表 | tokens.txt | 必须与这组模型匹配 |

相关组件磁盘体积约200MB；这不是模型加载RSS、总进程内存或8GB机器已可用的证据。
仓库存在其他量化文件，不等于任意替换decoder组合已获得兼容和质量验证。
初始解码使用greedy、单路流、线程受控作为建议起点；线程1、2、4的比较须在目标CPU开展，不直接固定满核。
模型chunk、特征参数、端点配置以该制品实际接口为准，下一阶段冻结配置，不能从20ms网络帧推导模型chunk。
2023年不自动意味着落后；但旧公开成绩也不能证明当前量化组合在手机麦克风和混说场景最优。
部分训练数据不可完整复现，不能声称已经查清全部训练数据授权与覆盖。

### 2.2 标点、ITN与热词

建议标点制品为sherpa-onnx-punct-ct-transformer-zh-en-vocab272727-2024-04-12-int8，其中使用model.int8.onnx。
该权重的许可文本、revision和哈希须先冻结核对；未完成之前标点保持关闭，原始ASR可独立验收。
若授权与性能通过，建议仅在stop后运行一次有界标点处理，减少普通CPU在每次partial重复计算。
内部端点可先累计原始片段，不能因为标点模型处理一次就向用户提交final。
ITN不是该Zipformer内建能力；独立规则或FST的Windows依赖及许可没有闭环，默认保持口语原文。
金额、编号、日期不能靠未经验证的激进替换自动改写；启用ITN须独立比较数字exact-match。
热词依赖Transducer的modified_beam_search路径，不能把词表直接放入greedy并宣称生效。
热词会增加搜索成本，必须同时报告召回、误插入、英文WER和P95延迟；默认没有领域词表时不开启。
S04、S05支持上述组件路径与解码限制，不证明当前项目后处理已经验收。
https://k2-fsa.github.io/sherpa/onnx/punctuation/pretrained_models.html
https://github.com/k2-fsa/sherpa/blob/master/docs/source/onnx/hotwords/index.rst

## 3. B挑战者：FunASR Paraformer两遍

### 3.1 能力与架构

候选组合是约220M Paraformer streaming、离线Paraformer第二遍、FSMN-VAD和CT标点。
中文及英文能力不能直接等价为手机真实混说通过；要使用与A相同录音、词表及归一化规则比较。
两遍不作为默认路径；只有重复实验确认质量收益且不破延迟、内存、稳定门槛后才启用或替换A。
热词、LM、ITN、VAD和标点分别具有依赖和许可，不能把“FunASR支持”当作任意模型组合都支持。
S07、S08、S12为官方服务和模型依据。

### 3.2 Windows制品必须区分年代

官方Windows原生funasr-wss-server-2pass.exe确实存在，不能写成FunASR两遍只能Linux运行。
S09的2024-05-15包说明标注4.5，要求VAD、声学与标点为v2.*.*；页面旧目录v0.2.0不能机械抄用。
S10为2026-07-22固定提交724a08585523e010f0de271f8d0bd0e438bb1727，修复在线模式文本与句状态相关问题。
S06记录v1.4.16于2026-09-18发布；没有证据证明2024 Windows EXE自动包含2026源码修复。
Python FunASR包、funasr-onnx包装、C++原生服务与其他运行时是不同制品；升级Python包不会更新旧EXE。
https://www.modelscope.cn/models/iic/funasr-runtime-win-cpu-x64
https://github.com/modelscope/FunASR/commit/724a08585523e010f0de271f8d0bd0e438bb1727
https://github.com/modelscope/FunASR/releases/tag/v1.4.16

B的放行必须记录可追溯二进制或源码构建来源、模型revision、依赖DLL、具体VAD和标点配置。
必须测试stop flush、句末状态、跨轮串音、长停顿和长稳内存，不能因官方提供包而跳过。
若以原生EXE作为worker内部服务，只能绑定loopback并由项目网络层代理，不直接向LAN暴露另一套未鉴权端口。

## 6. 许可分层与商业边界

代码许可、权重许可、量化衍生物、词表、LM、VAD、标点、ITN和训练数据必须分别处理。
下面是既有研究结论，不是制品授权审计完成；最终下载物仍须保留LICENSE、来源、revision、哈希与声明要求。
没有许可证据的制品不得以“开源仓库可见”作为可商用放行依据。

## 8. 联合放行与切换策略

第一步冻结A的具体组件、推理线程、解码、端点和后处理开关，用调参集优化，不接触验收标签。
第二步在4核8GB和6核16GB试验档位跑相同数据、相同采集链路；高配参考机结果单独呈现。
第三步比较A、B流式基础和B两遍，分别报告中文CER、英文WER、数字、首字、终稿、RSS、CPU与长稳。
建议B至少取得核心质量指标相对改善10%且其他质量项不劣化，并用按说话人配对置信区间确认收益；门槛待用户批准。
同时必须满足07_测试验收与性能基线计划.md第3节“语料、指标与质量门槛”和第4节“延迟、RTF、资源与长稳基线”，不能用平均准确率提升抵消P95明显恶化。
若精修在短轮预算内完不成，只能明确降级成已完整flush的一遍结果并注明原因；一遍也不完整则报错。
A质量不合格，即使速度更快也不能放行；B不合格则不默认开启第二遍。
若两者均不合格，保留问题语料并回到预算或候选评估，不能悄悄加GPU、云服务或放宽隐私。
本阶段结论是A先行、B有条件挑战、其余有边界保留；没有任何性能或商用许可通过声明。
